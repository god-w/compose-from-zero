## 产品范围

- 创建、编辑、归档习惯；每个习惯有名称、颜色和每日目标。
- 每日打卡，首页显示今日进度，详情页显示最近 7 天记录。
- 本地持久化；杀进程、重启设备后记录仍在。
- 可按进行中/已归档筛选；空列表、加载、失败都有明确 UI。
- 手机竖屏可导航，宽窗口展示列表和详情；支持大字号与 TalkBack。
- 有一处说明状态变化的动效，且不妨碍减少动画的用户。

## 交付要求

1. `README` 说明功能、运行步骤、架构图和设计取舍。
2. UI 状态由明确的状态持有者提供；子组件尽量只收值和事件。
3. 至少 3 条自动化检查：纯逻辑单测、添加/打卡 UI 测试、持久化恢复测试。
4. 记录一次性能基线与一次有证据的优化，或说明测量后无需优化。
5. 给出测试矩阵：空数据、长文本、离线、旋转、进程恢复、大字号、TalkBack、宽窗口。

## 评分表（每项 0–2 分）

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 状态与生命周期 | 数据错位或丢失 | 常规路径正确 | 旋转/恢复/快速操作都正确 |
| 架构 | UI 和存储强耦合 | 有状态持有者 | 数据流清晰、可独立测试 |
| 交互与可访问性 | 关键操作不可达 | 普通触控可用 | 大字号、键盘/TalkBack 可用 |
| 可靠性 | 无检查 | 手动验证 | 自动测试覆盖关键回归 |
| 性能 | 明显卡顿 | 使用流畅 | 有可复现测量与解释 |

**达标线**：总分至少 8/10，且“状态与生命周期”不得为 0。若某项只有 1 分，先补该项，再考虑增加功能。

## 最后的自检问题

你能不看答案解释：

1. 哪些值是业务数据，哪些只是界面状态？它们分别保存在何处？
2. 为什么列表项需要稳定 ID，为什么详情页只传 ID？
3. 一次打卡从触摸事件到数据库更新，再到 UI 重组，完整路径是什么？
4. 用户快速切换页面时，哪个协程会取消？谁负责取消？
5. 如果有人说“这个页面卡”，你如何测量、定位和验证修复？

能独立交付、定位故障并回答这些问题，才接近“精通 Compose”的实际工作标准。
